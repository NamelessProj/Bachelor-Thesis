\section{Methodology}
\label{chap:methodologie}

\subsection{Overview}

I structure this project as an iterative development rather than a linear implementation. The idea is to build an initial functional baseline, then progressively adjust the engine according to the constraints encountered: technical, format-related, and time-related. This approach seems better suited to a project of this kind, because it allows me to quickly check what actually works before going further.

The overall process rests on three axes: a development cycle based on the \glsit{pdca} model, a clear prioritisation of features whose objectives are defined in section \ref{sec:objMediaProject}, and functional validation at each iteration. This structure serves as a guiding thread throughout the project.


\subsection{Iterative Development Cycle (PDCA)} \label{sec:PDCA}

The \glsit{pdca} model (\textit{Plan}, \textit{Do}, \textit{Check}, \textit{Act}), formalised by W. Edwards Deming as part of continuous process improvement \parencite{deming_out_1986}, forms the methodological framework of this project. I chose this model because it fits well with development work where decisions need to be revisited as the project progresses. Each iteration therefore follows the four phases described in Table \ref{tab:defPDCA}.

\begin{table}[H]
    \centering
    \caption{PDCA cycle definition used}
    \renewcommand{\arraystretch}{1.5}
    \begin{tabular}{p{1.5cm} p{11cm}}
        \hline
        \textbf{Name} & \textbf{Description} \\
        \hline
        \textbf{Plan} & Definition of the features to implement for the iteration, in reference to the objectives set out in the chapter. \\
        \addlinespace
        \textbf{Do} & Implementation of the planned features. \\
        \addlinespace
        \textbf{Check} & Evaluation of the result through manual functional verification and, where applicable, automatic validation via the \gls{zod} \gls{parseur}. \\

        \hline
    \end{tabular}
    \label{tab:defPDCA}
\end{table}

This model was chosen for its ability to incorporate evaluation feedback without needing to redefine the entire scope at each step.

\subsection{Evaluation Criteria and Functional Validation}

In the absence of formal automated tests, I validate each feature using two complementary approaches.


\subsubsection{Manual Functional Verification}

Each implemented feature is tested directly in the browser, under real conditions, using representative \gls{json} files. The test cases cover both valid scenarios and intentionally constructed error scenarios (\glsit{negativetesting}): removing commas or quotation marks to break the \gls{json} \gls{syntaxe}, omitting required fields expected by the engine (such as the speaking character's name), and injecting values of the wrong type (for example, a boolean in place of a string). These test files are available in the project's GitHub repository\footnote{\textbf{GitHub}: source code hosting and version control platform based on \gls{git}. \parencite{noauthor_build_nodate}}: \nsrepo. The validation criterion is the conformance of the observed behaviour with the expected behaviour defined during the \textit{Plan} phase of each iteration.


\subsubsection{Validation via Zod} \label{sec:zod}

The \gls{zod} \gls{librairie}, integrated during the third iteration, validates the structure of the \gls{json} file supplied by the author at runtime. In case of a discrepancy from the defined \gls{schema} (a missing field, an incorrect type, an invalid structure), \gls{zod} returns an explicit error message precisely indicating the source of the problem, which constitutes a deterministic error-detection mechanism.

\subsection{Security and Robustness Considerations}

Two concerns guide development decisions beyond mere functionality.


\subsubsection{Code Robustness}

Using \gls{ts} as a typed superset of \gls{js} makes it possible to catch at compile time a set of type errors that would otherwise be silent in plain \gls{js}. Combined with \gls{zod} validation at runtime, this arrangement forms a double barrier against invalid engine states. \parencite{noauthor_starting_nodate}


\subsubsection{Code Security}

The engine operates entirely client-side, in the browser, with no \glsit{backend} server. This architecture removes a significant attack surface: there is no exposed database, no authentication handling, and no user data transmitted to a third-party server. The narrative content is static and does not pass through an application server. Validation of save files via \gls{zod} also helps prevent the injection of malformed data that could put the engine into an indeterminate state.


\subsection{Media Project Objectives} \label{sec:objMediaProject}

The main objective of this project is to offer an entirely text-based alternative to existing \gls{vn} engines, one that is easy to use and to deploy. Unlike current solutions presented in Section \ref{sec:moteur_vn_existant}, such as Ren'Py, which requires installing a dedicated development environment, or Twine, whose hypertext structure requires learning a dedicated macro language to go beyond a simple link, \nsits allows any author with basic \gls{json} knowledge to create and publish a functional \gls{vn}.

By offering an \glsit{opensource} solution, the project leaves people with development skills free to modify and extend its features according to their needs. Being \glsit{opensource} also allows anyone interested to actively contribute to the engine's development.

\subsection{Methodological Limitations}

This approach has two main limitations. The first concerns the absence of automated tests (\textit{unit tests}\footnote{\textbf{Unit test}: automated test verifying the behaviour of an isolated unit of code. (\cite{beck_test-driven_2002};\cite{aniche_effective_2022})}, \textit{integration tests}\footnote{\textbf{Integration test}: automated test verifying that several units or components work correctly together. \parencite{aniche_effective_2022}}). The development favours the progressive rollout of working features over setting up a formal test suite. This absence means that edge-case coverage depends on how exhaustive the manual tests performed were, and that regressions introduced during an iteration could go unnoticed.

The second limitation concerns the absence of validation by industry professionals. Since January 2026, I have been contacting \gls{vn} developers, in order to gather their opinion on the approach chosen to facilitate \gls{vn} development, as well as web developers, in order to discuss the infrastructure put in place to run the engine. To date, these outreach attempts remain unanswered. In the absence of feedback from professionals, the project's evaluation therefore relies solely on internal validation by means of a functional \glsit{poc}, without being confronted with an external specialist perspective. These two limitations will be revisited in the critical evaluation in Chapter \ref{chap:resultats}.
