\section{Introduction}

This chapter sets the framework for the project and explains why I chose to work on a web \gls{vn} engine driven by a declarative script. It presents the context, the research question, the objectives, and the method adopted, in order to clarify what this thesis actually seeks to demonstrate.

\subsection{Context}
The \gls{vn} genre combines narration, images, and sound to offer interactive experiences centred on the story. What interested me about this format is that it places text at the centre, while still leaving room for staging and interactivity. In practice, existing engines often offer very complete feature sets, but they also impose compilation steps, external dependencies, or deployment pipelines that complicate the task for a non-developer author. I therefore looked for a more direct alternative: a web-oriented \gls{vn} engine, able to interpret a declarative file without any installation or compilation on the author's side.

\subsection{Research Question}
The central question is as follows: to what extent does a web \acrlong{vn} engine architecture based on a declarative script format allow non-developer authors to create and deploy interactive content? Behind this question lies a very concrete point: can an author focus on their story while using a format simple enough to remain readable, usable, and publishable directly in a browser?

\subsection{Positioning and Constraints}
I favour native web technologies, in particular \textit{\gls{reactjs}}, as well as \textit{\gls{ts}}, which compiles to \gls{js} and therefore allows execution directly in the browser without any additional dependency on the client side. This choice enables simple deployment and native execution in the browser. The format chosen is \gls{json}, precisely because it remains readable in any text editor and integrates naturally into the web ecosystem. In return, this choice imposes a constraint specific to the format: a fragile \gls{syntaxe}, which requires runtime validation to limit input errors. The absence of a \glsit{backend} from the scope, on the other hand, stems from a deliberate choice rather than a consequence of the chosen format: it follows a security logic, since no data is stored or transmitted to a server, which reduces the engine's attack surface and removes the risks associated with server-side data handling.

\subsection{Target Group}
The engine is aimed first at authors of interactive stories with no development skills. It may also interest teachers who want to create simple, interactive content, as well as independent collectives looking for an immediate way to publish on the web.

\subsection{Methodology and Contributions}
I adopt an iterative method based on the \glsit{pdca} cycle: define an initial baseline, develop it, check what actually works, then adjust the rest of the work based on the observed results. The expected contributions are threefold: a documented declarative script \gls{schema} for \glspl{vn}, a web engine able to interpret this \gls{schema} without compilation, and a practical evaluation of its feasibility for non-developer authors.
